# Project execution rules

Read `docs/product/project-brief.md`, `docs/architecture/technical-architecture.md`, and the latest stage report before changing this project. The attached brief governs the product.

- The release-readiness audit of the existing manual application is complete; its three demonstrated fixes are merged, deployed and verified. No further implementation stage is authorized. Stages 13, 15 and 16 and release tags remain unauthorized. Execute only the explicitly authorized stage. Stage 12 — Dynamic Data Research is complete; Stage 14 — Portfolio Optimization is authorized independently using manual dated pricing (ADR-019). Stage 13 remains deferred. No provider is approved; Stage 15 is not authorized.
- Stop after each stage's completion report. Approval for a stage does not authorize the next stage.
- Inspect Git state, architecture documents, and relevant tests before edits.
- Keep factual data separate from editorial judgment. Unknown is a supported value; never replace unknown rates with zero.
- No Marriott scraping, undocumented endpoints, account connections, booking automation, secrets, or unlicensed photos.
- Keep business rules outside UI components. Stage 1 domain models are implemented; the independent Stage 4 points engine is implemented; the four-layer Stage 5 recommendation engine is implemented; the Stage 6 trip aggregation engine is implemented; Stage 7 local profile, certificate assessment and versioned persistence are implemented; the independent Stage 8 benefit engine is implemented; Stage 10 independent watch target validation and compatible v2 backups are implemented; Stage 11 optional coordinate evidence, geography and lazy maps are implemented; the independent Stage 14 portfolio engine is implemented; Stage 13 and Stage 15 remain unimplemented.
- Run `npm run check` after substantive changes and update documentation. Run browser flows when a stage introduces them.
- Use focused commits and pull requests. A remote deployment is verified only when its workflow and exact deployed URL are confirmed.
- Stage 12 was documentation only. Stage 14 adds a pure portfolio engine and read-only scenario comparison; preserve existing backup contracts. Before any separately authorized Stage 13 work, read `docs/data-methodology/dynamic-data-research.md` and ADR-018; satisfy the provider qualification gates. No scraping, provider code, monitoring, account integration or paid commitment is authorized by the research recommendation.
- Do not claim Stage 0 catalog validation verifies hotel facts. Stage 1 schema/reference checks require separately reviewed evidence; optional gaps are allowed.

## Current file boundaries

`app/` and `components/`: responsive explorer, property details, 2–4 property comparison, navigation, manual points inputs, trip editing, and application shell. `lib/validation/`: Zod foundation and Stage 1 domain schemas. `lib/catalog/`: validated domain ingestion, evidence checks, health, and pure explorer/comparison/presentation functions. `lib/points/`: strict manual input validation, dated policy references and pure single-stay economics. `lib/scoring/`: strict transient recommendation requests, versioned fit weights, eligibility, independent economics and deterministic explanations. `lib/trips/`: validated ordered trips and independent selected-booking aggregation. `lib/portfolio/`: validated read-only multi-trip scenarios with shared resource constraints and versioned strategies. `lib/watchlist/`: strict desired travel windows and nightly rate targets, independent from actual quote/evidence engines. `lib/profile/` and `lib/storage/`: strict local profile, independent dated one-night certificate assessment, explicit trip defaults and versioned planner persistence/import/export. `data/`: manifest, reviewed sourced catalog entities and Stage 9 expansion audit, and the dated, sourced Stage 8 benefit bundle. `scripts/`: schema and health commands. `tests/`: unit, integration, and browser projects. `.github/workflows/`: checks and gated Pages deployment.
